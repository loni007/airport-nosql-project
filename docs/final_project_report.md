# Airport Management System: Relational to MongoDB Migration

## Introduction

This project demonstrates an end-to-end migration from a relational SQL Server Airport Management System database to MongoDB. The work includes relational schema design, large synthetic data population, NoSQL data modeling, programmatic migration with transformations, validation, visualization, Docker-based database services, and final review documentation.

The project domain is airport management. The relational database contains airlines, airplanes, aircraft models, flights, clients, employers, travel agencies, tickets, reservations, and maintenance care records. MongoDB was chosen as the NoSQL target because the final workload is reporting-oriented and benefits from denormalized documents with embedded snapshots and precomputed fields.

Repository: `https://github.com/loni007/airport-nosql-project`

## Relational Database Design and Data Modeling

The SQL Server database is named `AirportManagement`. The schema is implemented in `sql/schema.sql` and uses ten relational tables:

| Table | Purpose |
| --- | --- |
| `AIRLINE` | Airline company metadata. |
| `MODEL` | Aircraft model metadata. |
| `AIRPLANE` | Physical airplanes assigned to airlines and models. |
| `FLIGHT` | Scheduled flights operated by airlines. |
| `CLIENT` | Passengers/customers. |
| `EMPLOYER` | Staff members involved in operations or maintenance. |
| `TRAVELAGENCY` | Agencies that can create reservations. |
| `TICKET` | Flight tickets and seat assignments. |
| `RESERVE` | Reservation transactions linking clients, tickets, and optional agencies. |
| `CARE` | Maintenance/service records for airplanes. |

The design uses more than the required four joinable tables. Key relationships include:

- `AIRLINE` one-to-many `AIRPLANE`
- `MODEL` one-to-many `AIRPLANE`
- `AIRLINE` one-to-many `FLIGHT`
- `AIRPLANE` one-to-many `FLIGHT`
- `FLIGHT` one-to-many `TICKET`
- `CLIENT` one-to-many `RESERVE`
- `TICKET` zero-or-one-to-one `RESERVE`
- `TRAVELAGENCY` one-to-many `RESERVE`
- `AIRPLANE` one-to-many `CARE`
- `EMPLOYER` one-to-many `CARE`

The ER diagram is documented in `docs/er_diagram.md` using Mermaid notation. It shows all primary keys, foreign keys, and cardinalities.

## Data Types and Constraints

The schema applies integrity rules required by the project:

- Primary keys on every table.
- Foreign keys for all relationships.
- `NOT NULL` constraints where required data must exist.
- Unique constraints for airline codes, names, client emails, passport numbers, airplane registrations, ticket numbers, travel agency names, and seat assignments.
- Check constraints for domains and business rules.

Examples of check constraints:

- `AIRLINE.founded_year` must be between 1900 and 2026.
- `MODEL.seat_capacity` and `MODEL.range_km` must be positive.
- `AIRPLANE.status` must be `ACTIVE`, `MAINTENANCE`, or `RETIRED`.
- `FLIGHT.scheduled_arrival` must be after `scheduled_departure`.
- `FLIGHT.origin_airport` must differ from `destination_airport`.
- `TICKET.price` must be greater than or equal to zero.
- `RESERVE.reservation_channel = 'AGENCY'` requires `agency_id`.

## Choice of MongoDB

MongoDB was chosen because the target workload is document-oriented reporting and visualization. The relational source requires joins to answer common questions, such as reservation activity by agency, airline performance, client reservation history, and flight information with airline names. MongoDB allows these reporting views to be stored as documents with embedded snapshots and derived fields.

MongoDB fits the project because:

- It supports nested document structures.
- It allows denormalized reporting models.
- It works naturally with Python through PyMongo.
- It supports indexes for idempotent upserts and analytical queries.
- It is easier to demonstrate visually through MongoDB Compass and chart scripts.

## Comparison with Redis

Redis is a key-value database optimized for caching, counters, queues, and fast direct lookups. The airport system could be represented with keys such as `airline:1`, `client:300`, or `agency:12:reservation_count`.

Redis would be fast for simple key access, but weaker for this project because the migration needs rich nested documents, embedded snapshots, derived fields, validation queries, and visualizations. Modeling reservations with embedded client, ticket, flight, and agency data would require many manual key conventions and extra logic.

## Comparison with Neo4j

Neo4j is a graph database. The airport system could be modeled as:

```text
(:Client)-[:MADE]->(:Reservation)-[:FOR]->(:Ticket)-[:ON]->(:Flight)
(:Flight)-[:OPERATED_BY]->(:Airline)
(:Airplane)-[:OWNED_BY]->(:Airline)
(:Airplane)-[:HAS_MODEL]->(:Model)
(:TravelAgency)-[:CREATED]->(:Reservation)
```

Neo4j would be useful for path analysis, such as discovering client-agency-airline patterns. However, the project focuses on transformed reporting documents, idempotent migration, validation, and dashboards. MongoDB is simpler and more directly aligned with these requirements.

## NoSQL Database Modeling

The MongoDB setup is implemented in `mongodb/setup_collections.py`. The target database is `airport_nosql`.

MongoDB collections:

| Collection | Source Tables | Purpose |
| --- | --- | --- |
| `airlines` | `AIRLINE`, `FLIGHT`, `AIRPLANE` | Airline performance and fleet counts. |
| `airplanes` | `AIRPLANE`, `AIRLINE`, `MODEL` | Fleet lookup with embedded airline/model details. |
| `flights` | `FLIGHT`, `AIRLINE`, `TICKET`, `RESERVE` | Flight schedule and reservation activity. |
| `clients` | `CLIENT`, `RESERVE`, `TICKET` | Customer reservation profile. |
| `travel_agencies` | `TRAVELAGENCY`, `RESERVE`, `TICKET` | Agency analytics. |
| `reservations` | `RESERVE`, `CLIENT`, `TICKET`, `FLIGHT`, `AIRLINE`, `TRAVELAGENCY` | Denormalized reservation records. |
| `maintenance` | `CARE`, `AIRPLANE`, `EMPLOYER` | Maintenance history. |
| `migration_runs` | Runtime metadata | Migration audit and idempotency evidence. |

Embedding decisions:

- `airplanes` embeds compact `airline` and `model` subdocuments.
- `reservations` embeds client, ticket, flight, and agency snapshots.
- `maintenance` embeds compact airplane and employer details.

Referencing decisions:

- Large one-to-many details are not embedded into parent documents. For example, airlines do not embed every flight. Instead, airline documents store aggregate counters.
- Every migrated document preserves the SQL primary key as a `sql_*` field.

Unique indexes on `sql_*` fields make the migration idempotent.

## Migration Process

The migration pipeline is implemented in `migration/migrate.py`. It connects to SQL Server and MongoDB, reads relational rows, transforms them into MongoDB document structures, and writes them using idempotent upserts.

Migration steps:

1. Load SQL Server and MongoDB configuration from environment variables.
2. Connect to SQL Server.
3. Connect to MongoDB.
4. Load SQL source counts.
5. Read all source tables required for transformations.
6. Build MongoDB documents using `migration/transformers.py`.
7. Normalize SQL/Python values such as `date` and `Decimal` for BSON.
8. Upsert documents into MongoDB using stable SQL IDs.
9. Store migration metadata in `migration_runs`.

The migration was run successfully with the following target counts:

| Collection | Migrated Documents |
| --- | ---: |
| `airlines` | 4 |
| `airplanes` | 5 |
| `flights` | 805 |
| `clients` | 2,005 |
| `travel_agencies` | 3 |
| `reservations` | 12,005 |
| `maintenance` | 303 |

The migration was also rerun using a stable run id to demonstrate idempotency:

```powershell
python migration/migrate.py --run-id demo-idempotency
```

Because documents are written through upserts keyed by SQL primary keys, repeated migration runs update existing MongoDB documents instead of inserting duplicates.

## Data Transformations

The migration is not a direct table-to-collection copy. It computes derived and denormalized fields.

| Collection | Derived Field | Description |
| --- | --- | --- |
| `clients` | `reservation_count` | Count of reservations made by the client. |
| `clients` | `agency_count` | Count of distinct travel agencies used by the client. |
| `clients` | `total_spent` | Sum of the client reservation ticket prices. |
| `airlines` | `total_flights` | Number of flights operated by the airline. |
| `airlines` | `total_airplanes` | Number of airplanes owned by the airline. |
| `airlines` | `completed_flights` | Number of completed flights. |
| `travel_agencies` | `total_reservations` | Number of agency-created reservations. |
| `travel_agencies` | `total_ticket_value` | Sum of ticket prices for agency reservations. |
| `airplanes` | embedded `airline` | Airline snapshot embedded inside airplane document. |
| `airplanes` | embedded `model` | Aircraft model snapshot embedded inside airplane document. |
| `flights` | `airline_name` | Airline name copied from joined airline data. |
| `flights` | `flight_duration` | Minutes between scheduled departure and arrival. |

These transformations make the MongoDB database more suitable for reporting and visualization.

## Error Handling

Explicit error handling is implemented in `migration/errors.py`, `migration/logger.py`, and `migration/error_demo.py`.

Required error scenarios:

1. Malformed source records.
2. Database connection failures.

The error demo logs:

- malformed flight source record skipped
- malformed reservation source record skipped
- SQL Server connection failure handled
- MongoDB connection failure handled

Logs are written to `logs/migration.log` and also printed to the console.

## Docker Support

Docker support is implemented in `docker-compose.yml`.

Services:

| Service | Purpose | Port |
| --- | --- | --- |
| `sqlserver` | SQL Server 2022 Developer source database | `1433` |
| `mongodb` | MongoDB target database | `27017` |
| `mongo-express` | Optional MongoDB browser UI | `8081` |

Key commands:

```powershell
docker compose up -d
docker compose ps
```

Then load SQL Server data and prepare MongoDB:

```powershell
sqlcmd -S localhost -U sa -P "YourStrong!Passw0rd" -C -i sql/schema.sql
sqlcmd -S localhost -U sa -P "YourStrong!Passw0rd" -C -i sql/seed.sql
sqlcmd -S localhost -U sa -P "YourStrong!Passw0rd" -C -i sql/generated_seed.sql
python mongodb/setup_collections.py --mongo-uri mongodb://localhost:27017 --database airport_nosql
```

## Conclusion

The project successfully implements a complete relational-to-NoSQL migration pipeline. SQL Server is used as the normalized source database with constraints and a large synthetic dataset. MongoDB is used as the denormalized target database with embedded documents and derived fields. The migration is programmatic, idempotent, logged, and validated. The visualization layer proves that the migrated MongoDB data is usable for analytics.

The most important technical result is that the final validation passed with 25 checks and 0 failures, confirming that the migration output matches the relational source for counts, checksums, aggregates, and spot checks.
